# 02 — Evaluation-harness architecture

## Data flow (benchmarks run out-of-band from PyReach)
```text
[Sources: GitHub / local OSV] --online pin+hash--> [inputs/ frozen, outside Git]
  -> [catalog & eligibility] -> [case manifest] -> [benchmark runner]
  -> [PyReach subprocess (--offline, isolated)] -> [SARIF/exit/stderr/rusage]
                                            \-> [optional internal graph adapter]
  -> [schema validation & normalization] -> [edge / reachability scorers]
  -> [case-level JSONL + summary JSON/CSV] -> [human report + CI quality gate]
[Baseline scanners] -----------------------> [separately scoped baseline table]
```

## Proposed repo structure (to be created after S0 review)
```text
benchmarks/
  pyreach_eval/
    __init__.py
    adapters/       # dataset format adapters, no PyReach production imports
    graph/          # canonical symbols/edges; may call a narrow audited bridge
    cases/          # case parser, source eligibility
    runner/         # CLI adapter, subprocess, isolation, run records
    scoring/        # exact-match comparison, confusion matrices
    reports/        # JSON/CSV/Markdown/SARIF validators
    tests/          # contract and regression tests
    fixtures/       # original small test programs, hand-reviewed only
    contracts/      # versioned JSON schema files generated by implementation
  reports/          # gitignored run material, except curated small summaries
  sources.lock.json # generated immutable source pin list
  run-config.json   # generated execution settings (path placeholders resolved)
```
**Separate storage root:** `~/.cache/pyreach-bench/inputs/` holds third-party sources, OSV DB snapshot, and tools downloaded in the ONLINE acquisition stage. No source code vendor-imported into PyReach by default.

## Module ownership and dependency rules
- `adapters` and `cases` → `graph` data types and standard library; never import runner, reports or PyReach private production modules.
- `runner` → `cases`, CLI contract, subprocess; only optional `graph` bridge depends on audited internal API.
- `scoring` → canonical case+graph+run-record types; no file I/O, network or subprocess.
- `reports` → scoring results and run records; must not change result labels.
- `tests` may import all harness modules but must never use network.
- Evaluation harness must not be imported by PyReach runtime. Enforce with test scanning imports or import-linter when practical.

## Trust boundaries
- Third-party Python repositories are untrusted **data**; do not run setup scripts, tests, exploits, dynamic imports or application launch hooks on the host.
- The scanner may load source files; isolate execution with no outbound network, file-system read-only where possible, quotas, time limits and resource caps.
- If baseline tool requires containers/runtimes, scope separately; no Docker socket mounted to untrusted containers.
- Never store tokens, DB secrets or personally identifying results in public artifacts.

## Graph projection decision
**Unknown until S0-T1:** the documented CLI emits SARIF but does not promise raw call-graph export. Options: (A) existing internal API as read-only bridge, (B) low-impact opt-in graph export behind test-only module, (C) if unavailable, mark graph benchmark UNSUPPORTED and keep reachability tests independent. Any production API/CLI change requires an ADR and user review.

## Artifact lifecycle
Every run records case ID + pinned source SHA + OSV DB SHA + PyReach SHA + machine config + exact argv + error category + timings + artifact checksums. Never overwrite earlier runs; version contract major when breaking.
